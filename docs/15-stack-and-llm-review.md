# 15. 기술 스택 재검토(Node.js vs Spring Boot) · LLM 필요성 검토

> 사용자 질문(2026-11-03): "Node.js가 더 좋지는 않은지, AI LLM이 꼭 필요한지 확인해 달라." 결론만 먼저:
> **A. 이 제품에는 Node.js(TypeScript, Next.js 풀스택 + 워커)가 더 잘 맞는다.** 차별점이 보고서 UI·공유 카드·LLM 파이프라인에 있고, 한국어 참고 구현(톡사이)이 TS라 그대로 이식 가능하다. Spring도 충분히 가능하며 사용자의 숙련도를 고려하면 합리적 선택이지만, UI·이미지 생성에서 30% 정도 더 든다.
> **B. LLM은 필요하다.** "메시지를 전부 읽고 판정한다"는 핵심 가치는 규칙 기반으로 대체 불가능하다. 다만 **LLM 없는 Tier 0 통계 리포트**(즉시·무료·외부 전송 0)를 앞단에 두면 비용·프라이버시·대기시간 문제를 동시에 줄인다. 두 단계 구조를 추천한다.

## A. Node.js vs Spring Boot — 이 제품 기준 비교

### A.1 평가 기준과 점수 (5점 만점, 이 제품에 대한 적합도)
| 기준 | 가중치 | Spring Boot (Java 21) | Node.js (TypeScript, Next.js) | 근거 |
|---|---|---|---|---|
| 보고서 UI·반응형·다크모드 | 높음 | 3 (Thymeleaf+HTMX, 컴포넌트 재사용 약함) | 5 (React 서버 컴포넌트, Tailwind, shadcn/ui) | 보고서는 카드 10여 종, 공유 페이지, 진행 상태 등 UI 비중이 크다 |
| 공유 카드 이미지(PNG) 생성 | 높음 | 2 (Java2D 수작업 또는 Playwright 추가 운영) | 5 (`next/og`의 `ImageResponse`/satori로 JSX→PNG, 폰트 포함) | 바이럴 루프의 핵심. Brandon도 "스크린샷용"을 강조 |
| LLM SDK·구조화 출력·평가 도구 | 높음 | 4 (Anthropic Java SDK, `outputConfig(Class)`) | 5 (Anthropic TS SDK, Zod 스키마, 평가·프롬프트 도구 생태계) | 둘 다 가능. TS가 스키마 정의·검증(Zod)이 한 곳에서 끝나 더 빠르다 |
| 참고 구현 재사용 | 중간 | 2 (톡사이 TS 코드를 Java로 재작성) | 5 (파서·통계·접지 검증·잡 하트비트 패턴을 직접 이식; 라이선스 확인 조건) | 03/08 설계의 상당 부분이 톡사이 패턴 |
| 파서 성능(50MB·30만 메시지) | 중간 | 5 | 4 (스트리밍 처리로 충분; 톡사이는 25만 상한으로 운영) | 둘 다 목표(20초) 충족 |
| 비동기 잡 큐·재시도·복구 | 높음 | 4 (DB 큐 직접 구현, 04 §4.1) | 5 (`pg-boss`: Postgres 기반 큐, 재시도·지연·싱글턴 키·스케줄 내장) | Node는 큐를 안 짜도 된다 |
| 트랜잭션·도메인 모델링 | 중간 | 5 (JPA, 도메인 메서드, 비관적 락이 익숙) | 4 (Prisma 트랜잭션 + 원시 SQL로 `FOR UPDATE` 처리) | 이 제품의 도메인 복잡도는 낮다(테이블 7개) |
| 타입 안정성·장기 유지보수 | 중간 | 5 | 4 | TS strict + Zod로 런타임 검증까지 가능 |
| 배포·운영 | 중간 | 4 (fat jar, Docker) | 4 (Docker: web + worker + postgres; Vercel은 워커 때문에 부적합) | 동급 |
| **개발자 숙련도(사용자)** | **높음** | **5** | **2~3** | 가장 큰 변수. 학습 비용과 운영 자신감 |
| 1인 개발 속도(프론트 포함) | 높음 | 3 | 5 | 한 언어·한 저장소·한 빌드 |
| 한국 웹 채용·협업 풀 | 낮음 | 4 | 4 | 동급 |

가중 합산(숙련도 가중치 포함)은 **Node 약 4.4 vs Spring 약 3.8**. 숙련도 항목을 제외하면 Node 4.7 vs Spring 3.7. 즉 **제품만 보면 Node, 사람을 포함하면 격차가 줄지만 여전히 Node**다.

### A.2 결정에 영향을 주는 질문
1. 운영·유지보수를 사용자가 혼자 장기간 할 것인가? → 그렇다면 Spring의 익숙함이 실제 가치다. 다만 이 코드베이스는 Claude Code가 작성·테스트하고 사용자는 리뷰·운영한다면, TS 코드 읽기는 Java 개발자에게 진입 장벽이 낮다.
2. 공유 카드 PNG와 OG 이미지를 MVP에 넣을 것인가? → 넣는다면 Node의 이점이 크다(Spring은 Playwright 컨테이너 추가 운영).
3. 결제·회원 등 "전형적 백오피스" 기능이 커질 것인가? → 커져도 Node로 충분하지만, 사용자 조직에 Spring 공통 모듈(결제·인증)이 이미 있으면 Spring 유지가 이득.

## B. LLM이 꼭 필요한가

### B.1 규칙 기반(LLM 없음)으로 가능한 것
| 산출물 | 방법 | 품질 |
|---|---|---|
| 통계 전체(메시지 수·비율·선톡·답장 중앙값·히트맵·월별·미디어·ㅋ 밀도·새벽) | 08 §3 계산기 | 정확, 즉시 |
| fun facts(골든아워·최장 침묵·첫 메시지·종결자·최장 메시지) | 결정적 | 재미 있음, 매번 다름 |
| 뱃지·어워드(선톡왕·답장요정·새벽감성·ㅋㅋ제조기·사진셔틀·링크수집가·유령회원 등) | 임계값·순위 규칙 | 좋음. 단 "결정권자·중재자·총무"처럼 **내용 이해가 필요한 역할은 불가** |
| 관계 유형·점수 prior(답장·선톡 균형·온도) | 07 §3.1 공식 | 수치는 OK, 설명은 템플릿 |
| "바뀐 주" | 메시지량·선톡·답장지연 시계열의 변화점 탐지(예: 주 단위 CUSUM/최대 차이) | 시점은 잡히지만 **왜 바뀌었는지는 모름** |
| 판정 문장·한 줄 평 | 템플릿 200~300개 + 숫자 삽입("선톡 71:29, 이건 대화가 아니라 방송이야") | 처음엔 웃기지만 3번째 보고서부터 반복이 보인다. 콜백·조어·맥락 유머 불가 |
| 인용 카드 | 규칙으로 고를 수 없다(어떤 메시지가 웃긴지 모름). 최장 침묵을 깬 메시지 등 **위치 기반**만 가능 | 약함 |

### B.2 LLM이 있어야만 되는 것 (= Brandon의 핵심 가치)
- 대화 **내용**에 근거한 판정: 누가 사과했고 누가 넘겼는지, "보자"가 몇 번 나오고 실제로 봤는지, 톤이 어디서 식었는지.
- 인물별 의견: 숫자 너머의 역할(결정권자, 중재자, 밈 공급자, 말만 하는 사람).
- 조어 헤드라인·콜백·별명: 대화 속 반복 표현을 찾아 이름 붙이기(14 V13).
- 전환점의 **이유**와 결정적 한 줄 선택.
- 사용자의 질문(Deep)에 대한 답.
- 안전 신호 감지(자해·학대 맥락)는 키워드만으로는 오탐·미탐이 크다.
요약: LLM 없이는 "통계 분석기"는 되지만 "다 읽고 솔직하게 말하는 친구"는 되지 않는다. 경쟁 분석(01 §3)에서 통계만 제공하는 무료 앱(톡랭크·카카오톡 정밀 분석기·WhatsAnalyze)과의 차별점이 사라진다.

### B.3 비용·프라이버시 관점의 재점검
| 항목 | 수치/사실 |
|---|---|
| LLM 비용(08 §5) | 3천 메시지 ≈ $0.4, 2만 메시지 ≈ $1.2, 10만 메시지(샘플링) ≈ $4. 청크 단계를 Haiku 5.5($0.10/1M 입력)로 내리면 2만 메시지 ≈ **$0.45** |
| 가격 대비 | Brandon 보고서 1건 €9.99 수준. 비용은 매출의 5~10% |
| 프라이버시 | LLM 사용 시 Anthropic API로 전송(학습 미사용, 30일 보존). 선택지: 이름 가명화(13 ADR-13), 전화·계좌 마스킹(08 §4) |
| 지연 | LLM 1~5분 vs 규칙 기반 즉시 |
| 로컬 모델 대안 | Ollama 등 온프레미스 한국어 모델은 유머·장문 판정 품질이 크게 떨어지고 GPU 운영 부담이 생긴다. MVP 비권장 |

### B.4 추천 구조: 두 단계
```
업로드 → 파싱 → [Tier 0 통계 리포트]  즉시, 무료, LLM 0, 외부 전송 0
                 - 숫자로 보는 우리(차트), fun facts, 규칙 뱃지·어워드, 관계 유형 prior, 템플릿 한 줄(까비서 톤 60개)
                 - "까비서가 다 읽고 보고서를 쓸까?" CTA
             → [Tier 1 까비서 보고서]  LLM, 1~5분, (v2) 유료
                 - 07/14의 전체 보고서. Tier 0 결과는 입력(통계 사실)으로 재사용
```
효과: ① 무료 사용자에게도 즉시 가치·공유 카드(통계 카드) 제공 ② LLM 호출은 진행을 택한 사용자에게만 → 비용 절반 이하 ③ LLM 장애 시에도 Tier 0는 동작 ④ "외부로 안 보내는 모드"를 원하는 사용자 수용 ⑤ 대기 화면에 Tier 0를 띄워 이탈 감소.
설계 반영: 02 FR-R0(Tier 0) 추가, 05 `conversation_stats`를 Tier 0 렌더 소스로 사용(이미 존재), 07에 `tier0Templates`(규칙 한 줄 템플릿 60개, 까비서 톤) 추가, 09에 Tier 0 페이지 섹션 추가. 구현 순서는 12 스텝 2(통계) 직후 Tier 0 UI를 끼운다.

### B.5 "LLM 완전 제외" 를 고집할 경우의 MVP 정의
Tier 0만으로 출시. 재미 보강: 템플릿 300개 + 상황 변수(요일·시간대·비율 구간), 변화점 탐지로 "바뀐 주" 수치만 제시, 어워드 12종. 한계를 랜딩에 명시("까비서는 숫자만 봅니다"). 이 경우 07/14의 절반은 보류되고 제품은 '카톡 통계 결산(Wrapped)' 범주가 된다. 추천하지 않는다.
