# 19. 긴 대화 처리 설계 — "줄여서 올리세요"라고 하지 않기

> 2026-11-03. 질문: 사람들은 몇 년치 대화(수십만 메시지)를 그대로 올린다. 용량을 줄이라고 하지 않고 어떻게 받을 것인가.
> 현재 구현(`src/lib/report/planner.ts`, `src/worker/pipeline.ts`)을 기준으로 문제를 수치로 놓고, 단계별 해법과 권고를 적는다.

## 1. 문제를 숫자로

| 항목 | 값 | 근거 |
|---|---|---|
| 한국어 메시지 1개 ≈ 토큰 | 평균 35~45 (본문 25~35 + `m123 [시각] 이름:` 머리 10~15) | `estimateTokens = chars/1.6` (`transcript.ts`) |
| 10만 메시지 전사 | 약 4M 토큰 | 위 환산 |
| 30만 메시지(현재 상한) | 약 12M 토큰 | 위 환산 |
| 청크 추출 입력 단가 | Sonnet 5.5 $2/M · **Haiku 5.5 $0.10/M** | `cost.ts` |
| 종합 입력 단가 | Opus 5.5 $4/M, 출력 $20/M | `cost.ts` |
| 사고(thinking) 토큰 | 출력 단가로 과금, 끌 수 없음(effort로만 조절) | 모델 규칙. `LLM_MAX_TOKENS` 사고의 원인 |
| 현재 읽기 상한 | `LLM_MAX_TOTAL_TOKENS` 1.5M → 10만 메시지면 커버리지 ≈ 35%, 30만이면 ≈ 12% | `makePlan` 비례 샘플링 |
| 현재 비용 상한 | `LLM_MAX_COST_USD` 5 → 넘으면 샘플링(최소 10%) 후 거절 | `makePlan` |
| 통계·Tier 0 | **항상 100%** (전 메시지 결정적 계산) | `computeStats`, `buildTier0` |

핵심 사실 두 가지: (1) 숫자(선톡·답장·리듬·바뀐 주의 통계적 근거)는 길이와 무관하게 전부 계산된다. 샘플링은 LLM이 **읽는** 부분에만 걸린다. (2) 비용의 90%는 "읽기"(청크 추출)이고, 읽기 모델을 Haiku로 바꾸면 같은 양을 **20분의 1 비용**으로 읽는다.

## 2. 원칙

1. 사용자에게 줄이라고 하지 않는다. 상한(파일 150MB, 메시지 100만)은 보호 장치일 뿐, 보통 사용자는 만나지 않는다.
2. 숫자는 항상 전부. LLM 읽기는 "예산 안에서 가장 중요한 것부터".
3. 어디까지 읽었는지 숨기지 않는다. "핵심 구간 94% · 전체 41% 읽음"처럼 보여준다.
4. 비용 상한은 거절 조건이 아니라 **계획 선택** 조건이다. 상한에 맞춰 (모델 등급, 읽기 비율, 계층 수)를 고른다. 최소 계획도 넘을 때만 거절.
5. 긴 대화일수록 싼 모델로 넓게 읽고, 비싼 모델은 쓰기에만 쓴다.

## 3. 해법 — 단계별

### 1단계 (바로, 코드 하루): 읽기 모델 등급 + 예산 기반 계획 + 상한 상향
- 청크 추출 모델을 크기에 따라 고른다: 전사 ≤ 600k 토큰은 Sonnet(현행), 그 이상은 **Haiku 5.5**(`LLM_CHUNK_MODEL_LARGE`). 종합은 Opus 유지.
- `makePlan`: 비용 상한을 넘으면 던지지 않고 (a) Haiku로 전환 → (b) 읽기 비율 축소 순으로 계획을 바꾼다. `COST_LIMIT_EXCEEDED`는 Haiku + 최소 비율(10%)로도 넘을 때만.
- 기본값: `LLM_MAX_TOTAL_TOKENS` 1.5M → **4M**(Haiku면 $0.4), `LLM_MAX_COST_USD` 5 → **8**, `UPLOAD_MAX_MESSAGES` 30만 → **100만**, `UPLOAD_MAX_BYTES` 50MB → **150MB**(파싱 15만 개 1.3초·4.3초 E2E 실측, 100만 개는 ~10초·메모리 ~1GB 예상 → web 컨테이너 메모리 2GB 권장).
- 위저드 7단계에 계획 미리보기: "메시지 23만 개 · 핵심 위주로 41% 읽음 · 약 12분" (`GET /conversations/{id}/plan`, 통계로 즉시 계산). 사용자는 줄이는 게 아니라 **깊이**를 고른다.

예상 비용(30만 메시지 ≈ 12M 토큰): 현행 Sonnet 1.5M 샘플 ≈ $4.5(커버 12%) → 1단계 Haiku 4M ≈ $0.4 + 종합 $1.5 ≈ **$2(커버 33%)** → Haiku 전량 12M ≈ $1.2 + 종합 ≈ **$3(커버 100%)**. 시간은 청크 수/동시성에 비례: 12M/60k = 200청크, 동시 3개·청크당 40초 → 45분, 동시 8개 → 17분.

### 2단계 (일주일): 중요도 기반 읽기 + 2계층 요약
- 결정적 중요도 점수(LLM 없음): 세션 밀도, 질문-답 쌍, 긴 메시지, 감정 표식(ㅠㅠ·미안·보고싶·싫), 24시간 넘는 침묵을 깬 메시지, 새벽 대화, 계획 어휘(보자·언제·몇시), 이름 호명, 미디어 폭발. 세션 단위로 점수.
- 예산 배분: 첫 2주 + 마지막 4주는 **항상 포함**(시작과 현재), 상위 점수 세션 우선, 나머지는 월별 균등 샘플(바뀐 주 탐지용 타임라인 보존). 커버리지를 "핵심 구간 / 전체" 두 숫자로 보고서에 표시.
- 청크가 40개를 넘으면 월 → 분기 요약을 한 번 더 거친다(2계층 map-reduce). 종합 프롬프트가 수십만 토큰으로 커지는 것을 막는다.
- 사고 토큰 통제: 청크 추출은 effort `low`(구조화 추출엔 충분), 종합만 `high`. 출력 한도는 스트리밍 + 64k(이미 반영).

### 3단계 (제품 결정 후): 깊이 선택·느린 모드·저장소
- 깊이 선택: "핵심만(몇 분, 무료)" vs "전부 읽기(길면 수십 분, 유료 또는 대기열 후순위)". 원 서비스가 보고서당 과금으로 전량 읽기를 감당하는 구조와 같다.
- 느린 모드: Message Batches API(반값, 수 시간)로 전량 읽기 → 완료 이메일(13 Q4 이메일 인증 전제). 비용 민감한 사용자용.
- 원문을 DB bytea 대신 객체 저장소(S3 호환)에 암호화 저장, 대용량(30MB 초과)은 업로드 응답 후 워커에서 파싱(위저드는 "읽는 중" 폴링).
- 전역 LLM 동시성 조절(워커 전체 합산 토큰/분)로 429 폭주 방지. `docker compose --scale worker=N`은 이미 가능.

## 4. 권고
1단계는 비용 구조를 바꾸는 가장 큰 레버(Haiku 읽기)라 먼저. 2단계의 중요도 점수는 "재미있는 보고서"의 품질을 길이와 무관하게 지키는 핵심이므로 그다음. 3단계는 과금 모델 결정(13 Q3)과 묶인다.

## 5. 반영 상태 (2026-11-03)
1단계 중 코드로 들어간 것: 압축 전사(08 §4, 22~45% 절감), 크기별 청크 모델(100만 토큰 초과 → Haiku 5.5), 청크·수리 effort low, 대화 단위 청크 캐시(같은 대화의 두 번째 보고서는 종합 비용만), 종합 입력 다이어트(청크 24개 초과), 스트리밍 + 출력 한도 상향. 상한 기본값(`LLM_MAX_COST_USD` 5, `LLM_MAX_TOTAL_TOKENS` 1.5M, 메시지 30만)은 그대로 두고 `.env`로 올린다(개인용 권장값은 README). 2·3단계는 상용화 전제라 보류.

## 6. 시간(2026-11-03 추가) — "2분"에 가깝게
시간은 토큰 수가 아니라 **출력 토큰(사고 포함)과 직렬 호출 수**가 결정한다. 적용한 것: 청크 병렬 3→8, 청크 추출 출력 상한(요약 2문장·항목 수 제한, effort low → 호출당 ~10초대), 종합 effort high→medium(사고 토큰 1~3분 절감), 종합 출력 항목 수 축소(발견 4~5·어워드 3~4·순간 4~6), 선택형 Opus fast mode(`LLM_FAST_MODE=synthesis`, 출력 2.5배·단가 2배, 429/400이면 표준으로 자동 복귀). 예상: 1만 메시지 ≈ 2분, 5만 ≈ 4분, 10만 ≈ 5~6분(fast mode면 종합 1분 단축). 더 줄이려면 종합을 두 호출(A: 판정·역학·바뀐 주·인물 / B: 발견·제안·상·점수·순간)로 병렬화하는 방법이 남아 있다(입력 토큰 2배, 미구현).

## 7. 지금 당장의 운영값 (코드 변경 없이)
`.env`: `LLM_MAX_COST_USD=10`, `LLM_MAX_TOTAL_TOKENS=3000000`, `LLM_CHUNK_MODEL=claude-haiku-5-5`(긴 대화 위주라면), `WORKER_CHUNK_CONCURRENCY=6`(API 한도가 허락하면). 10만 메시지 기준 커버리지 ≈ 75%, 비용 ≈ $2, 시간 ≈ 10분.
